# План: симуляция воды по OpenFOAM (полная замена движка воды)

Дата: 2026-06-13. Автор задачи: пользователь («разработать план симуляции воды
по OpenFOAM», цель — **полная замена** текущего движка воды).

> ЧЕСТНО И СРАЗУ: OpenFOAM **нельзя** сделать живым (real-time) движком воды
> внутри интерактивного 60 fps приложения. Это пакетный CFD-решатель. Поэтому
> «полная замена» реализуется не как «OpenFOAM крутится в render-loop», а как
> «текущую качественную Box2D-воду заменяет картинка/поля НАСТОЯЩЕЙ CFD,
> посчитанной OpenFOAM-ом ОФФЛАЙН и воспроизводимой в реальном времени». Ниже —
> почему так, какие есть пути, и какой рекомендуется. В конце — открытый вопрос,
> который всё ещё надо решить (реалистичная картинка vs честная live-физика).

---

## 0. Контекст: что есть сейчас

- Гидравлическая проекция (`ProjectionKind::Hydraulic`, «Water») — аналогия:
  ток → расход Q, напряжение → давление, `ΔP·Q ≡ V·I` точно
  (`HydraulicMapping.h`). Это **точное** отображение, не эвристика.
- Движок воды — гранулы Box2D (`ParticleSim`, `connected`-режим): трубы,
  фитинги-камеры на узлах, насос-крыльчатка, вентури-горловина резистора.
  Качественно, интерактивно, дёшево; «честность» — только в СРЕДНЕМ (дрейф
  калиброван к току солвера). Это заявлено в `PHYSICS_VISUAL_LAYER_STATUS.md`.
- Есть карантинный «ВАРИАНТ Б» `HydraulicSim.*` (один контур, поток от тока) —
  тоже не CFD.

Задача: заменить качественную Box2D-воду на симуляцию по OpenFOAM.

---

## 1. Что такое OpenFOAM и почему live-замена невозможна

OpenFOAM — открытый (**GPLv3**) пакет вычислительной гидродинамики на методе
конечных объёмов (FVM). Решает Навье–Стокса на 3D-сетке. Ключевые свойства,
которые определяют весь план:

1. **Пакетный, не интерактивный.** Кейс задаётся структурой каталогов
   (`0/`, `constant/`, `system/`), считается решателем (`simpleFoam` —
   стационар, `pimpleFoam` — нестационар, `interFoam` — свободная поверхность
   VOF) из командной строки, визуализируется в ParaView. **API «посчитай один
   кадр за 16 мс» не существует.** Реальное время счёта — секунды–часы на один
   прогон даже для скромной 2D-сетки. В интерактивном приложении, где юзер
   таскает элементы и крутит номиналы, пересчитывать OpenFOAM на каждое
   изменение нельзя.
2. **Тяжёлая зависимость.** Гигабайты, тулчейн сборки, генераторы сетки
   (`blockMesh`, `snappyHexMesh`). Конечному пользователю это не поставишь
   «в комплекте».
3. **Linux-first.** На Windows только: WSL2 (рекоменд., пакеты свежее), Docker,
   либо нативный `blueCFD-Core` (MinGW-порт, OpenFOAM 12, 2024-1).
4. **GPLv3.** Линковка OpenFOAM в приложение делает производное произведение
   GPLv3 (у проекта сейчас нет файла LICENSE — это отдельный вопрос). Запуск
   OpenFOAM как ОТДЕЛЬНОГО ПРОЦЕССА и потребление его выходных ДАННЫХ —
   безопасная граница, не «линковка».

Вывод: OpenFOAM — инструмент ОФФЛАЙН-эталона и генерации данных, не live-движок.
Существующие «real-time с OpenFOAM» работы — это суррогаты/ROM поверх оффлайн-
прогонов (ITHACA-FV POD-Galerkin; POD+ML; SmartSim/SmartRedis для CFD+ML),
а не OpenFOAM в петле рендера.

## 2. Ключевой инсайт аналогии (не потерять при «замене»)

Для гидравлической аналогии ТОЧНАЯ «вода» — это **1D-сеть Гагена–Пуазёйля**:
ламинарный поток в трубе даёт `ΔP = (8μL / πr⁴)·Q`, что ЛИНЕЙНО и отображается
ТОЧНО на `V = I·R`. То есть честную физику воды в этой аналогии приложение
**уже считает** — это тот же MNA-солвер цепи. 3D-OpenFOAM не нужен для ФИЗИКИ
аналогии; он нужен (если нужен) для реалистичной КАРТИНКИ: профили скорости,
вихри за дросселем, поле давления, свободная поверхность.

Поэтому «замена движка воды» — это в первую очередь замена ВИЗУАЛЬНОГО СЛОЯ
(Box2D-гранулы → поля/линии тока настоящей CFD), а не замена расчёта токов.
Любой путь обязан остаться согласованным с солвером (не врать про Q и ΔP).

## 3. Пути реализации «замены» (ранжированы)

### Путь A — Оффлайн-предрасчёт + воспроизведение (БЕЙК ПОЛЕЙ)
Для каждого канонического элемента трубопровода (прямой участок, вентури-
резистор, тройник-узел, насос, бак-конденсатор, турбина-катушка) один раз
оффлайн считаем OpenFOAM при наборе режимов (числа Рейнольдса / расходов),
экспортируем поля (скорость, давление, линии тока) в компактный формат, кладём
в репозиторий. В рантайме рендер берёт поле, ближайшее к текущему Q из солвера,
и интерполирует/анимирует трассеры по нему.
- ➕ Настоящие CFD-поля; real-time; не требует OpenFOAM у пользователя.
- ➖ Только параметризованные случаи; геометрия узлов комбинаторна; объём
  данных; нужна аккуратная привязка к топологии схемы.
- Сложность: средняя. **Наиболее реалистичный «настоящий CFD на экране».**

### Путь B — Редуцированная модель / суррогат (ROM на базе OpenFOAM)
ITHACA-FV (POD-Galerkin ROM для OpenFOAM) или POD+ML (автоэнкодер+LSTM) обучаем
на оффлайн-снимках OpenFOAM; в рантайме модель за миллисекунды выдаёт поле по
параметрам (Q, геометрия). Это «честный» способ получить real-time из OpenFOAM.
- ➕ Параметрическая гибкость без хранения тысяч кейсов; реально real-time.
- ➖ Существенная R&D-работа (обучение, валидация, инфраструктура Python/ML
  рядом с C++); риск артефактов вне обучающего диапазона.
- Сложность: высокая.

### Путь C — Live GPU-CFD ВМЕСТО OpenFOAM (если цель — настоящая текущая вода)
Если под «полной заменой» имеется в виду «настоящая жидкость течёт в реальном
времени» (а не именно OpenFOAM), то это даёт не OpenFOAM, а GPU-CFD: **FluidX3D**
(решётчатый Больцман, OpenCL на любых GPU, real-time, raytraced, свободная
поверхность VOF+PLIC) или SPH (DualSPHysics). Это ближе всего к «живой воде».
- ➕ Реальная live-CFD-картинка, интерактив.
- ➖ Это **не** OpenFOAM; FluidX3D — **free только для non-commercial**; OpenCL/
  GPU-зависимость; всё равно надо согласовывать с физикой солвера.
- Сложность: высокая; меняет техстек (GPU).

### Путь D — Экспорт кейса (лабораторный режим)
Из трубопроводной сети схемы генерим готовый OpenFOAM-кейс (сетка + ГУ);
продвинутый пользователь запускает CFD внешне, результат импортируется обратно
как поле для просмотра.
- ➕ Дёшево; даёт «настоящий OpenFOAM» энтузиасту; обучающая ценность.
- ➖ Не real-time, не «движок»; ручной шаг.
- Сложность: низкая–средняя. Хорошее ДОПОЛНЕНИЕ, не замена.

## 4. Рекомендация: гибрид D→A (→B опционально)

«Полную замену» предлагаю трактовать как **замену визуального слоя воды на
воспроизведение настоящих OpenFOAM-полей**, при сохранении честной физики из
солвера/1D-сети:

1. **OpenFOAM — оффлайн-инструмент** (эталон + генератор данных), запускается
   разработчиком в WSL2/Docker, НЕ у конечного пользователя.
2. **Рантайм** воспроизводит забейканные поля (Путь A); 1D-сеть/солвер задаёт
   мгновенные Q и ΔP (физика), OpenFOAM-поле задаёт КАК это выглядит (профиль
   скорости, вихри, давление).
3. **Экспорт-кейс (Путь D)** — дешёвый бонус для энтузиастов и для валидации.
4. **ROM (Путь B)** — апгрейд, если бейка не хватит по гибкости.

Это даёт «настоящую CFD-воду» на экране, остаётся real-time, не тащит GPLv3 в
бинарь и не требует OpenFOAM у пользователя.

> Если же цель — именно ЖИВАЯ текущая вода (физика жидкости в реальном времени),
> то честный ответ: это **не OpenFOAM**, а GPU-CFD (Путь C, FluidX3D/LBM). Это
> развилка к пользователю (см. §8).

## 5. Архитектура интеграции (для путей A/B/D)

- **Граница — отдельный процесс, не линковка** (GPLv3 + стабильность): приложение
  никогда не линкует OpenFOAM; общается через файлы/данные.
- **Кейс-генератор** `circuit → pipe-network → OpenFOAM case` (новый модуль,
  напр. `src/cfd/OpenFoamCaseWriter.*`): из узлов/труб строит геометрию и ГУ
  (вход/выход по знаку тока, расход из Q солвера).
- **Раннер** (оффлайн/Путь D): скрипт в WSL2/Docker, прогон `blockMesh` +
  решатель, `foamToVTK`.
- **Импортёр полей** `src/cfd/FoamFieldReader.*`: VTK/полевые данные → компактный
  бинарь в репозитории (`assets/cfd/`), индекс по (элемент, режим Q).
- **Рендер-слой**: в `ProjectionBuilder` (Hydraulic) новый эмиттер, рисующий
  линии тока/скорость/давление из поля вместо Box2D-частиц; гейтинг по видимой
  Water-панели (как сейчас у `ParticleSim`).
- **Согласование с честностью**: средний расход поля = Q солвера (инвариант,
  как у текущего дрейфа); задокументировать в `PHYSICS_VISUAL_LAYER_STATUS.md`.

## 6. Сборка / зависимости / лицензия / Windows

- **Разработка эталонов**: WSL2 (Ubuntu) + `openfoam.com`/`.org` пакеты —
  свежее и гибче нативного порта. Docker — для воспроизводимости. blueCFD-Core —
  если нужен нативный Windows-прогон без WSL.
- **У конечного пользователя OpenFOAM НЕ требуется** (пути A/B): в комплекте —
  только забейканные поля/ROM. Путь D требует OpenFOAM только у энтузиаста.
- **Лицензия**: OpenFOAM GPLv3 — безопасно, пока он отдельный процесс/источник
  данных, а не линкуемая библиотека. У проекта стоит завести явный LICENSE
  (сейчас нет) — отдельная задача. FluidX3D (если Путь C) — non-commercial.
- **Размер данных**: бейк полей считать заранее по объёму; компактный формат +
  даунсэмпл.

## 7. Фазовый план (вехи)

- **Ф0. Валидация аналогии (без кода движка).** Один прямой участок: посчитать
  OpenFOAM-ом профиль Пуазёйля, сверить `ΔP=8μLQ/πr⁴` с солвером. Цель — убедиться,
  что CFD и аналогия согласованы. Деливерабл: заметка + первый кейс.
- **Ф1. Сквозной тонкий срез.** Кейс-генератор (1 труба) → оффлайн-прогон →
  импорт поля → рендер линий тока в Hydraulic для ОДНОГО сегмента. Доказать
  пайплайн end-to-end.
- **Ф2. Каталог элементов.** Вентури-резистор, тройник-узел, насос, бак, турбина —
  оффлайн-кейсы + бейк по сетке режимов Q.
- **Ф3. Воспроизведение в рантайме.** Интерполяция поля по Q солвера, анимация
  трассеров, согласование среднего расхода (инвариант честности) + тесты.
- **Ф4. (Опц.) ROM/параметризация** (ITHACA-FV или POD+ML) — если бейка мало.
- **Ф5. Интеграция и переключение.** Тоггл «Box2D / OpenFOAM-поля» в Water-виде,
  гейтинг по панели, тесты, документация статуса. Box2D остаётся фоллбеком.
- **Ф6. (Опц.) Экспорт-кейса** (Путь D) для энтузиастов.

## 8. Открытый вопрос к пользователю (развилка ВНУТРИ «полной замены»)

«Полная замена движка воды» всё ещё допускает две разные цели — это меняет план:

- **(I) Реалистичная КАРТИНКА настоящей CFD** (поля/вихри/давление), физика
  по-прежнему из честного солвера → пути A/B/D, OpenFOAM оффлайн. Рекомендуется.
- **(II) Живая ТЕКУЩАЯ ВОДА в реальном времени** (жидкость как физический
  объект на экране) → это GPU-CFD (FluidX3D/LBM, Путь C), не OpenFOAM; меняет
  техстек и лицензию.

До старта реализации нужно зафиксировать (I) или (II).

---

## 9. Риски и открытые вопросы

- 3D-поля OpenFOAM vs 2D-проекция приложения (нужен срез/осреднение).
- Комбинаторика геометрии узлов (тройники/перекрёстки) при бейке — ограничить
  каноническими случаями, остальное — интерполяция/фоллбек на Box2D.
- Объём забейканных данных в репозитории.
- Согласование с честной физикой: поле НЕ должно противоречить Q/ΔP солвера.
- Перф импорта/рендера полей (профилировать как Box2D — встроенным замером кадра).
- Поддержка у конечного пользователя (пути A/B её не требуют — это плюс).

## 10. Оценка усилий (грубо)

- Ф0–Ф1 (доказать пайплайн на 1 трубе): значимый, но ограниченный кусок.
- Ф2–Ф3 (каталог + воспроизведение): основной объём.
- Ф4 (ROM): отдельный крупный R&D-блок, только если нужно.
- Путь C (GPU-CFD): фактически новый движок + GPU-стек.

Минимально полезный результат — Ф0–Ф1 (доказательство, что «настоящий CFD на
экране» работает end-to-end на одном сегменте), дальше расширять по элементам.
