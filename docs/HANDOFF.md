## ФИКСЫ ПО ЖИВОМУ ПРОГОНУ ПОЛЬЗОВАТЕЛЯ (2026-06-11, ночь) — 443 зелёных

Пользователь запустил приложение и нашёл два бага; оба закрыты с тестами.

### 1. Стрелки тока: показывали вверх, ехали вниз
`emitCurrentArrows` (ProjectionBuilder): ГЛИФ переворачивался по знаку тока
(flowDir), а АНИМАЦИЯ — нет: phase всегда положительный, марш всегда вдоль
a->b компонента. У источника ток отрицателен относительно его оси -> стрелки
смотрят против оси, а едут по оси. ФИКС: phase меняет знак вместе с flowDir
(включая режим электронов). ТЕСТ: AppPathDirections.CurrentArrowsMarchWhereTheyPoint
(два кадра с малым dt; каждая движущаяся стрелка обязана ехать туда, куда
показывает, в обоих режимах — conventional и electron).

### 2. Вода: «область сжатия — шарики утрамбовываются на полрадиуса»
Три источника, все закрыты:
- **Рендер раздувал шарики 1.25x** над Box2D-коллайдером (emitWaterFlow):
  касающиеся коллайдеры (2r между центрами) рисовались с перекрытием 0.5r —
  ровно картина пользователя. Теперь рисуем РОВНО радиус коллайдера
  particleWorldRadius(p.wireThickness). ТЕСТ:
  HydraulicProjection.WaterBallsAreDrawnAtTheColliderSize.
- **Телепорты впечатывали шарики в толпу** (худшая пара была 1.53 РАДИУСА
  вглубь!): wrapParticles в connected-режиме телепортировал транзитные
  частицы на фикс-станцию входа следующей трубы не глядя на занятость;
  боковой кламп срабатывал в устьях камер; rescue в flowOwnership ставил не
  глядя. УБРАНО: телепорт через узлы в connected удалён совсем, кламп не
  трогает частицы в камерах, rescue ищет свободный диск (spotIsFree через
  QueryAABB) или ждёт следующего подшага.
- **Вместо телепорта — камерный ассист** steerThroughChamber: в камере узла
  частицу мягко ведёт «воронкой» к устью исходящей трубы (осевая компонента
  + центрирование к оси, gain 2.0; НЕ точка-таргет — точка даёт затор и
  рваный поток). Масштабируется |targetSpeed| исходящей трубы: ток 0 — вода
  стоит, pump-only не фальсифицируется.
- **Гранулярная балансировка** (без неё поток упирался в потолок разрушения
  арок и переставал масштабироваться по току): коридор у столбиков резистора
  4.2 -> 5.0 радиусов; pumpImpellerRadius 1.05hw -> 0.95hw (коридор над
  лопастями 1.48 -> 1.64 диаметра, инвариант >=1.4 в силе); pumpOmegaForFlow
  кламп ±9 -> ±6 (на ω=9 лопасть мнёт плотную массу — пары у колеса сидели
  0.5-0.6r вглубь). МОРАЛЬ: «сильнее давить» в гранулярной воде = крепче
  арки; при заторе расширяй горловины, а не усиливай напор.
- ТЕСТ: WaterNetwork.WaterBallsStayEssentiallyIncompressible — после прогона
  худшая пара во всей сети не глубже 25% радиуса (слоп Box2D ~0.1 wu +
  динамический запас); в сообщении об ошибке печатает координаты худшей пары
  и дистанцию до крыльчатки (так и нашли, что давит именно колесо).

### 3. «Глючно и медленно»: 100% ядра -> ~11-16% (дефолтная раскладка)

## Цепь на звёздочках (2026-06-11) — 407 тестов зелёные

БАГ «цепи слетели с шестерёнок»: три места считали геометрию зацепления
независимо — овал ChainSim арки вокруг узла ~0.26*wireThickness, шестерня
рисовалась радиусом ~0.72*wireThickness, направляющие emitChain на ±0.45.
Цепь физически проваливалась внутрь нарисованной шестерни.

- **`src/physics/ChainGeometry.h`** — единый источник истины: linkRadius /
  linkPitch / chainHalfWidth / sprocketPitchRadius / sprocketTipRadius /
  sprocketRootRadius / sprocketTeeth (зубьев столько, чтобы угловой шаг на
  питч-окружности = шагу цепи: один ролик на впадину). ChainSim, MainWindow
  (ChainSpec.halfWidth, linkRadius) и ProjectionBuilder берут размеры ТОЛЬКО
  отсюда. Менять геометрию зацепления — только в этом файле.
- ChainSim: oval.off = sprocketPitchRadius(...), зазор рельс 1.25*linkRadius
  (было 1.5 — цепь болталась на дугах).
- emitChain: велосипедная цепь — ролики (тёмная заливка + контур + пин),
  чередующиеся внешние/внутренние ПАРЫ пластин (ширины kOuterPlateWidth /
  kInnerPlateWidth из ChainGeometry — по ним пластины находят тесты);
  направляющие на ±pitchR (совпадают с треком симуляции).
- emitGears: настоящая звёздочка — диск по корневому радиусу, трапециевидные
  зубья root->tip (quads), ступица с осевым отверстием и 4 окнами облегчения;
  фаза зубьев = интеграл пробега цепи / pitchR (поверхностная скорость зуба =
  скорости цепи, без проскальзывания).
- Z-order: emitGears вызывается ПЕРВЫМ в buildMechanics — circles рисуются в
  порядке push, тело шестерни должно лежать ПОД роликами цепи.
- Тесты tests/test_chain_gear.cpp (7 шт): порядок радиусов, зуб=шаг цепи,
  рост зубьев с радиусом, ДВА регрессионных (звенья сидят на питч-треке после
  3 с симуляции; радиус дуги у узла == pitchR рендера), звёздочка в проекции
  из общей геометрии (тело по rootR, ровно `teeth` зубьев-quads), велоцепь
  из сим-звеньев (ролики/пины поштучно, 2N пластин, оба типа присутствуют).

## Architecture (после рефакторинга)

```text
CircuitModel (src/circuit/Circuit.h, single source of truth, stable ComponentId)
  -> CircuitSolver (src/solver/) : DC | stepTransient (companion BE/Trapezoidal) | solveTransientSnapshot
       diode states: solveIterative (ideal PWL fixed point)
  -> ProjectionBuilder (src/projection/) : ЕДИНСТВЕННЫЙ источник render-данных
       ProjectionKind::{Schematic, Physics, Mechanics} -> ProjectionResult{RenderPrimitives, ElementState[]}
       ElementGeometry.h (символы C/L), MechanicsMapping.h (аналогия, P=V*I сохраняется точно)
  -> PrimitiveRenderer (src/render/) : тупой ImGui-бэкенд; RenderPrimitives/ColorMaps — pure data
  -> CanvasInteraction (src/ui/) : edit/hit-test, потребляет InteractionInput (без ImGui, тестируемо)
  -> CircuitCanvas (src/ui/) : тонкая оболочка (камера + клок анимации + сборка ViewParams)
  -> MainWindow : layout Single/Dual/Triple, transient-контролы, DualViewState (3 камеры, sync)
Learning: src/learning/ (TaskGenerator: ground truth из солвера; LearningSession: предохранители 1-6 КОДОМ;
          Lessons.h: арка вывода; AnkiExport: AnkiConnect addNotes, FSRS на стороне Anki)
Assistant: src/assistant/LlmClient.* (OpenAI-compatible, llama.cpp/vLLM/API; критик-не-решатель)
Net: src/net/HttpClient.* (POSIX, plain HTTP, localhost-сервисы)
```

Инвариант: один элемент модели = один ComponentId = N проекций из одной модели+solution. Никаких коллекций элементов на проекцию. Editing/selection/camera — через общую модель и DualViewState.
